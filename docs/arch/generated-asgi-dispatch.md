# Generated ASGI Dispatch Architecture

Pyganini turns one validated `RouteGraph` into one deterministic Starlette router
at `app/_pyganini/asgi.py`. The graph remains the only Pyganini route model.
Generation projects facts from `iter_endpoints()` and runtime dispatch uses
public Starlette and AnyIO interfaces.

## Generation boundary

`src/pyganini/_dispatch_generation.py` consumes the graph after static validation.
It groups endpoint surfaces by normalized path while retaining graph order,
ordered parameter evidence, canonical methods, route ownership, handler
bindings, optional kit creators, selected mounted source identities, endpoint
templates, selected layout tuples, and source positions.
The selected layout tuple comes from the private graph-level `_selected_layouts`
helper in `src/pyganini/_route_graph.py`; source inspection consumes that same
selection for its page and action chain display.
Each unique path becomes one Starlette
`Route`. Static siblings already precede their dynamic sibling in the graph, so
the generated route order supplies matching priority. A private Starlette
`Route` subclass promotes a method-mismatched path match to full ownership.
This prevents a later dynamic route from handling an unsupported method for an
earlier static path while retaining Starlette's normal 405 and `Allow` logic.

The dispatch plan contributes one `GeneratedArtifact` to the existing combined
plan. `_generation.py` remains the sole plan validator, stale comparator,
atomic writer, marker owner, and obsolete-output cleaner. `pyganini check` computes
the same expected bytes and performs no application write. No graph, registry,
or manifest is persisted.

The private `_PathGroup` projection and canonical method-to-endpoint mapping are
also consumed by source-only `pyganini routes explain`. Its target is decoded once
to an ASGI path, then each shared group is matched with the existing
`PathPriorityRoute.matches()` in generated order. This gives explanation the
same static priority, path-before-method ownership, allowed-method union, and
HEAD-to-GET endpoint selection as generated dispatch without constructing a
Router, importing generated state, or invoking an application handler. The
explanation is a transient diagnostic projection and adds no generated product
or runtime hook.

Generated bytes depend only on normalized graph values and template names, not
template content. They do not depend on
the checkout path, current directory, locale, filesystem enumeration, hash
seed, time, or imported application state.
Static route `name`, `title`, and `RouteMeta` labels are inspection-only graph
facts. Dispatch planning and controlled-import equality checks deliberately
exclude them, so changing display metadata does not change generated bytes.

## Generated surface

`app/_pyganini/asgi.py` begins with the generated ownership comment. Its public
names are typed
`create_router(environment=..., error_handler=..., template_inspection=...)`
and
annotated `router`, backed by `starlette.routing.Router`. `error_handler` is
the optional public `RouteErrorHandler` callback; the generated module imports
only its type and private runtime aliases. All other imports and intermediate
values use private aliases or private names. Each router sets
`redirect_slashes=False`.

The generated package `__init__.py` does not re-export the router. Applications
import it directly:

```python
from app._pyganini.asgi import router
```

Controlled imports and handler capture occur once. Each `create_router()` call
validates or creates a Jinja environment, builds new Starlette endpoints from
the retained immutable facts, and returns a new router. The default public
`router` is `create_router()`.

The factory validates that inspection is a `TemplateInspectionMode` before
route or middleware construction. Generated endpoint and error-render facts
carry deterministic page, fragment, layout, embedded-fragment, handler, owner,
and mount evidence into the existing renderer. Construction correlates those
facts with captured route, template, layout, method, handler, mount, and error
facts and independently emitted embedded-fragment expectations, and fails
closed before serving when they disagree. Each embedded expectation carries
the canonical local path, exact 15-field fragment endpoint evidence, and exact
template evidence; marker copies are not accepted as route authority.
Construction derives each local path from the retained fragment route and
mount root, rejects non-normalized paths, and requires the fragment's source,
owner position, mount, mounted source selection, and mount root to equal the
enclosing endpoint selection. Matched-error validation compares all 15
error-evidence fields with the route endpoint's independently captured
per-method evidence before validating its markers. It also requires its
template pair to equal the retained root error-rendering authority and its
per-method layout tuple to equal the endpoint's retained selected layouts. A
render-configuration disagreement remains
`PYGANINI015` even when Starlette constructs a route middleware stack. No runtime
graph lookup or filesystem discovery occurs.

Inspection facts have one current generated shape. Endpoint and error
construction reject missing fields, missing independently captured evidence,
and superseded shorter tuple shapes with `PYGANINI015`; dispatch contains no
adapter for an older generated product. Route evidence is exactly fifteen
fields. Template, layout, marker, embedded-fragment, root-error, and
matched-error tuples are structurally validated before any field is read.
The matched-error template pair is exactly one two-element tuple.
Matched-error inspection, layout, and captured-evidence maps cover exactly the
route's supported non-HEAD methods, with HEAD normalized to GET.

The router can serve as an ASGI application or mount under Starlette or
FastAPI. A root mount follows more specific host routes. Mount and proxy
prefixes remain in ASGI `root_path`; generated paths stay graph-local. Pyganini
adds no lifespan hook and does not take ownership of host middleware, state,
exception handling, dependencies, OpenAPI, server, or deployment.

## Controlled import and validation

Graph and plan construction import no application module. Controlled imports
start when the host imports `app._pyganini.asgi`. Generated calls validate owners
in canonical order before constructing the router:

1. Import each recorded route module.
2. Read its direct `Route` binding from the module dictionary.
3. Require the expected `pyganini.RouteDef`, `pyganini.KitRouteDef`, or
   `pyganini.KitRouteMount` and compare its complete runtime surface, template
   declarations, mount identity, exact selection, navigation values, and
   destination values with the generated projection.
4. Resolve local, direct-import, aliased-import, relative-import, and
   module-alias handlers through direct module dictionaries.
5. Require runtime object identity to match the recorded source binding.
6. For a live kit or mounted owner, validate the creator identity and
   one-request signature. For a mounted source, validate the creator-free
   source `KitRouteDef` and selected source binding.
7. Validate each outer handler callable without invoking it, following
   `functools.partial.func` but not `__wrapped__` or descriptors.

This boundary rejects module `__getattr__`, changed bindings, missing symbols,
surface drift, async generators, unsupported callable descriptors, and
signatures that cannot be called with their expected request arity. It does not
reload modules, scan runtime files, register routes, expand mounted sources, or
invoke handlers at import time. A newly
added route owner absent from stale generated bytes is detected by the normal
`pyganini check` comparison.

`PYGANINI012 route-import` reports import, ownership, or binding failures.
`PYGANINI013 route-callable` reports callable classification or signature
failures. Both occur during generated-module import and retain underlying
causes when present.

## Navigation preparation

For navigation-bearing path groups, generated dispatch retains method-keyed
canonical root-to-owner fact tuples and accepted trail-key sets derived from
live inbound destinations. A path may combine endpoints owned by different
route declarations, so each effective method uses the facts for its own
endpoint owner. `HEAD` selects the `GET` facts and handler. After Starlette
matching and path-parameter-name validation, dispatch prepares one private
request scope state before the kit creator or route handler runs. The kit
creator and handler therefore share the same request-local resolver, while
different requests cannot share resolutions.

Preparation reads the effective decoded ASGI `root_path`, binds canonical
graph-local patterns and dynamic values through the shared pure URL contract,
and prefixes the resulting browser-visible href once. It captures returns from
the complete ASGI `path` without adding the prefix and contains inbound returns
inside a non-empty prefix. It reads only the two reserved query keys and performs no application I/O,
template work, filesystem discovery, event-loop creation, or worker-limit
mutation. Dynamic labels are resolved only by application code. Pages,
fragments, actions, and direct responses receive no implicit Jinja navigation
context; an application places a `Navigation` value in its explicit render
mapping when it needs HTML.

## Invocation and response boundary

Local handlers accept one Starlette `Request`. A kit creator accepts one
request. Page, fragment, and non-captured action handlers accept
`(kit, request)`; captured action handlers accept `(kit, request, body)` or
`(kit, request, form)`. Async callables run on the ASGI event-loop thread. Sync
callables run through
`anyio.to_thread.run_sync(..., abandon_on_cancel=True)` with the host's default
limiter. Pyganini does not mutate that limiter or create an event loop. If a sync
wrapper returns an awaitable, Pyganini awaits it on the ASGI event loop.

Cancellation before offload prevents work from starting. Cancellation during
running sync creator work releases the waiting task without starting the kit
handler. Once sync work starts, the existing worker limitation applies.
Context variables and application exceptions retain AnyIO and Python behavior.

For a kit or mounted endpoint, the generated method plan invokes the live
owner's `create(request)` once,
awaits it when needed, then invokes the selected handler once with the
unchanged kit and request. Creator and handler selection is method-specific,
so a normalized path can combine local and kit methods. Kits are not cached
across requests, methods, endpoints, routers, or HEAD and GET.

The final result can be a concrete Starlette `Response`, `Page`, or
`FragmentResponse`. Pages accept `Page`, fragments accept `FragmentResponse`,
and actions accept either render value. The public `PageRouteResponse`,
`FragmentRouteResponse`, and `RouteResponse` aliases describe those page,
fragment, and action contracts without changing runtime dispatch. Every endpoint still accepts a direct
Starlette response, which bypasses Jinja. `PYGANINI014 route-response` reports a
kind mismatch, missing declared template, invalid render contract, non-response
result, or path-parameter names that disagree with generated evidence.
`PYGANINI015` owns environment and Jinja failures. Application handler exceptions
pass through unchanged for host handling.

## HTTP behavior

Pages and fragments accept GET and HEAD. Actions accept their declared POST,
PUT, PATCH, or DELETE method. Surfaces at one path share one method union. An
unsupported method at a matched path produces Starlette 405 with the exact
accepted `Allow` members; OPTIONS is not implicit. An unmatched path or a
noncanonical trailing slash produces 404. Path ownership is decided before
method handling, so an exact static path cannot fall through to a later dynamic
route merely because the dynamic route accepts a different method.

Starlette decodes dynamic values into `Request.path_params`. The generated
endpoint verifies the matched parameter-name set against ordered graph
evidence, but handlers read values by name.

HEAD selects and executes the GET handler with the original HEAD request. A
private response wrapper calls the original response and replaces every ASGI
body payload with empty bytes. It preserves status, headers, message framing,
stream iteration, and background work, including the original `Content-Length`.

## Dependency and future boundaries

AnyIO is a direct runtime dependency for both sync handler and synchronous
Jinja cancellation behavior. Jinja is the only built-in v0 renderer. Rendering
uses the graph and generated endpoint facts described in
`rendering-responses.md`; it adds no renderer registry or runtime scanner.

Handlers using direct Starlette request parsing retain the public `Request` and
use its async `form()` context manager. Generated dispatch does not inspect HTMX
headers or pre-read form data unless an action explicitly opts into
`request_data=`. That declaration adds one normalized request-data fact to the
canonical action and endpoint surface. The generated method plan passes
deterministic capture literals to `build_endpoint`; runtime import checks the
declaration value and callable role/arity before serving requests.

For an opted-in ordinary action, dispatch selects the handler, captures the
declared body or form on the ASGI thread, materializes and closes every parsed
upload, and then invokes `(request, body|form)` once. A route-kit creator runs
once before capture and its handler receives `(kit, request, body|form)`. Body
and form values are frozen and resource-free. Async captured handlers run on
the ASGI event loop; sync captured handlers use the AnyIO worker. A sync handler
may not call Starlette async request or upload methods, and ordinary
non-opted-in surfaces keep the existing invocation path.

Body capture uses public `Request.stream()` with a cumulative byte limit. Form
capture uses public `Request.form(...)` parser limits after public media-type
parsing. Per-upload reads are bounded by `max_upload_size`; distinct upload
objects reuse one immutable value and receive one shielded public `close()`
attempt. Primary failures retain their identity with deterministic cleanup
notes. Cleanup-only failures become an ordered `ExceptionGroup`. AnyIO's
default worker limiter remains host-owned and unchanged.

The generated URL interface, HTMX, middleware, dependency, inspection,
mounted-source, navigation, and example work must consume this router or the
same graph through their accepted owners. They must not add a second route
model, runtime scanner, handler registry, rendering model, generated root, or
write lifecycle. Mounted expansion is generation-time projection; request
dispatch uses only captured owner, source, path, parameter, and layout facts.

## Generated-route error composition

When configured, `create_router(error_handler=...)` uses one private Router
subclass for generated 404 composition and the existing `PathPriorityRoute`
boundary for generated 405 and matched-route exceptions. The seam uses public
Starlette `Router`, `Route`, `Request`, `Response`, `HTTPException`, and ASGI
interfaces. It does not copy matching, mutate host exception-handler scope,
add a registry, or create another route model.

The callback receives the original request and exception. It gets one chance
for generated 404 and 405, endpoint `HTTPException` values including 413 and
415, `DispatchError`, and application exceptions from route middleware,
creators, handlers, request-data work, rendering, or response dispatch before
response start. `None` delegates unchanged. A callback response must preserve
an HTTP exception's status and required headers; 405 retains the canonical
`Allow` members. HEAD responses retain status and headers while suppressing
body bytes. A non-HTTP callback response must have status 500, is sent once,
and the original exception is re-raised after completion. Exceptions after
response start bypass the callback. The callback catches `Exception`, never
`BaseException`, and callback failures cannot recurse.

The graph projects the root error page template, root error fragment template,
and root layout tuple once. Each generated path group also carries immutable
method-keyed selected layout evidence into the existing `PathPriorityRoute`.
A callback `Page` uses the root error template with root layouts for 404 and
405, or with the selected endpoint layouts for a matched failure. A callback
`FragmentResponse` uses the root fragment template with no layouts. Both call
the existing renderer and environment; there is no runtime template name,
second graph, registry, matcher, renderer, host wrapper, or generated product.
Controlled imports compare the two runtime root declaration fields with the
generated evidence, including an errors-only ordinary root with no endpoint.
The generator emits error render facts and method-keyed error layout arguments
only when the live root declares at least one error template. Applications
without either declaration retain the pre-feature generated callback call
shape and bytes; their existing direct `Response` and `None` callback behavior
continues through the default preparation contract.

The default `router` remains callback-free. Startup, import, callable
validation, middleware loading, environment preparation, Router construction,
host routes, static files, outer middleware, lifespan, server, and deployment
remain outside generated-route composition and application-owned.

Callback configuration, missing error templates, and result-contract failures
use `PYGANINI019 route-error-handler`. Request result diagnostics include the
method, generated-route normalized path when known, error category, expected
status, actual result type or status, and generated source
`app/_pyganini/asgi.py`; they do not expose absolute checkout paths. The expected
HTTP status and required headers are snapshotted before the application
callback runs, so callback mutation of the received `HTTPException` cannot
change the authoritative 404, 405, 413, or 415 contract. Existing startup and
application callback exceptions retain their existing behavior and are not
translated into `PYGANINI019`.
Error-template and selected-layout failures use the existing localized
`PYGANINI015` render phases and preserve the renderer cause.

## Route middleware projection

When a final endpoint has a live route-tree middleware chain, generation emits
the used marker captures and loads their direct `MIDDLEWARE` bindings during
controlled generated-module startup. It passes one flattened root-to-owner
tuple through Starlette's public `Route(..., middleware=...)` argument and
constructs fresh route and middleware instances for each `create_router()`
call. A marker-free graph remains free of middleware-specific captures and
imports, while the independent generated-route error callback extension is
still emitted.

The loader reads `vars(module)` and validates the recorded tuple count and
Starlette `Middleware` members. Import, binding, validation, and construction
failures are `PYGANINI018 route-middleware` with preserved causes. Request-time
middleware exceptions remain application errors. Route middleware can
short-circuit a matched request, but does not wrap generated 404 or 405
responses, static mounts, or outer host failures. Generated-route error
composition wraps the selected route boundary outside route middleware and
therefore can present a route middleware exception.
